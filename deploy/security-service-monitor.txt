Private security service connectivity and loaded-signature monitor

The existing web process starts app.security_services.SecurityServiceMonitor
through FastAPI lifespan in staging/production when DEMO_MODE=false. No new
service, environment variable, credential, permission or public port is needed.

Every 60 seconds after completion, it sends framed ClamAV PING and VERSION
and an authenticated Redis PING. It never uploads files or reads/modifies Redis keys.
Each probe has a 3-second total timeout and bounded connection cleanup. An
unexpected probe failure also cancels its sibling. Shutdown cancels the task.
No monitoring connection or task is started in local demo mode.

Logs contain only security_service_probe, level, checked_at, fresh, read_only,
and the fixed per-service ready/status fields. URLs, credentials, IPs, raw
responses, exception messages and customer content are never included.

/readyz and the admin readiness panel use this process's last result. They do
not launch more probes on requests. Unchecked, failed, stopped, differently
configured or older-than-120-second observations cannot pass these checks.
The existing /healthz and /deploymentz semantics and the live-payment lock stay
unchanged. This is operational monitoring, not approval to launch payments.

One-shot diagnostic in the existing web environment:
    python -m app.security_services
Exit 0 means both PING responses and loaded-signature freshness passed; exit 1
means otherwise. Use the service
logs for the recurring observer. Do not export sealed credentials locally.

If a dependency fails, confirm its service, private DNS/network and existing
credential injection, then rerun the read-only diagnostic. Do not disable the
scanner or rate limiter, expose internal ports, or broaden Redis ACLs to make a
health result green. Application uploads/rate limiting keep their existing
fail-closed behavior independent of this observation.

Loaded daily signatures must be no older than 72 hours. This is a conservative
local launch-readiness threshold, not a guarantee of the latest vendor version.
More than 5 minutes into the future is clock_invalid; old definitions are
definitions_stale; unknown/unparseable/disabled
VERSION responses are unavailable. All are non-ready and warning log events.
The ClamAV entrypoint pins TZ=UTC0 and LC_ALL=C because the protocol's timestamp
has no timezone. Deploy that entrypoint before depending on this check. The
parser uses fixed English month names and validates the date and weekday.
No engine version, database version or raw response is published. This observer
does not change per-upload scan policy: old definitions make launch readiness
fail but do not by themselves reject uploads. Scanning failures still reject.

Not covered: malware-detection correctness, exact latest-version comparison,
shared-counter correctness, load/capacity, freshclam health, or human alerts. Their
separate checks and the external alert destination remain launch requirements.
