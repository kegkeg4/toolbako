ツールバコ DBリクエスト障害の切り分け（2026-10-23）

2026-10-23追加分はローカル実装。公開環境へは未反映。

対象: 既存Railway rare-manifestation / web。公開・決済開始の判定ではない。
ログ: Database request failed; no success response was sent に続くJSON。
記録するのは event, phase, reason, elapsed_ms, request_id のみ。
URL・クエリ・メール・SQL・接続文字列・例外本文・スタックは記録しない。
request_id はサーバー生成32桁hexだけ。利用者のX-Request-IDは使わない。

遅い要求の追加診断（database_request_slow）:
要求開始から接続終了・アプリ内ロック解放まで2秒以上の場合だけ、正常に境界を
抜けた要求のevent/elapsed_ms/phase_ms/request_idを記録する。
phase_msの固定項目はlocal_lock, connect, advisory_lock, load, handler, save, cleanup。
local_lockは待ち時間、connectは接続、loadは状態読込と復元、handlerは画面/API処理
（その途中の外部通信・明示保存を含む）、saveはmiddlewareによる最後の保存、
cleanupは状態復元と接続終了。レスポンス本文の転送時間・全SQLの内訳ではない。
各項目はms単位で丸めるので、合計とelapsed_msには丸め誤差がありうる。
通常の2秒未満の要求は追加記録しない。URL・ユーザー・本文・SQLを記録しない。
失敗要求は従来のdatabase_request_failedで調べる。slowは成功率の集計には使わない。
これは計測追加であり、処理待ち・503の解消、ピーク負荷への合格を意味しない。
DB接続数・5秒の排他待ち上限・保存順序・金融処理は変更していない。

phase と主な調査先:
- local_lock / local_lock_timeout: 同一web内の5秒の処理待ち。直前の長い処理・負荷を確認。
- connect / connection_timeout 等: DB接続先・TLS・ネットワーク・接続数を読取確認。
- advisory_lock / database_busy: 別プロセスが保持するDBロック。処理中のworker・要求を確認。
- load: スキーマ・状態読込。query_timeout / schema_version_mismatch 等を確認。
- handler: 画面/APIの処理中。DB原因とは限らない。要求IDと時刻で照合。
- save: 保存・会計同期・監査・通知キューのトランザクション。
- cleanup: 状態復元・接続終了。例外があってもアプリ内ロックは解放する。

対応:
1. 発生時刻・phase・reason・elapsed_msと要求IDを記録する。
2. エラー率・正常応答の有無と稼働ログを照合する。負荷を追加せず確認する。
3. 決済結果不明時は、再購入や別キーでの再実行を促さず、既存の照合手順へ。
4. DB排他を外す、待ち時間を無制限にする、成功レスポンスを返す等で隠さない。
5. 秘密値を含む例外本文をログへ追加しない。必要な分類は固定コードとして追加する。

検証:
ローカルの人工接続失敗、SQL期限切れ、ロック競合、復元失敗、接続終了失敗、
キャンセル、保存失敗で503・秘密情報非出力・ロック解放を確認。
修正前のコードでは2つの後片付け失敗でロックが残ることも比較検証した。
過去の503の原因をこの比較だけで断定しない。14:11-14:14の旧版ログでも
複数回の発生を確認しており、稼働環境での継続調査が必要。
